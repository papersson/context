Your direction is fundamentally sound — it's the functional core / imperative shell pattern (Bernhardt) applied to a gating pipeline, with content-addressed pinning borrowed from build systems. Since you run NixOS, the framing you already know applies almost verbatim: today your evaluation is a "mutable global namespace" build (like a traditional FHS system where installing one package changes results for another), and you want a Nix-style derivation: output = f(pinned inputs), hashed, cached, re-runnable. I'll go through your questions, but let me lead with the one place your plan has a hole, because everything else hangs off it.

## The trap: where does the "known, previously-accepted patterns" memory live?

Your problem 1 exists because the waive decision reads state left by other candidates. Freezing violations and pinning the ruleset doesn't fix that by itself — it just fixes problems 2 and 4. If, after the redesign, there is still a side table of "patterns humans previously accepted" that the engine consults, you've reintroduced the hidden mutable input through the back door, and the decision is again non-deterministic across candidates and across time.

The fix is to *reify that memory as the ruleset itself*. When a human signs off and judges the pattern to be recurring, that judgment must become an explicit rule change — a new ruleset version, reviewed and versioned like code — rather than an implicit row in a shared database. The only channel by which past decisions may influence future ones is promotion into a versioned ruleset. This gives you a clean invariant to state and enforce: **the waive decision is a pure function of exactly two values: the candidate's frozen violation snapshot and one pinned ruleset version.** Nothing else. If a rule "needs" cross-candidate data (say, a baseline of expected violation counts), that data must be snapshotted and become part of the pinned inputs, not read live.

This also answers "how to make waiving stateless": you don't make it stateless so much as you make all state *explicit, versioned, and passed in as an argument*.

## Core/shell boundary

Draw the line at values-in, values-out. The core takes `(violation_snapshot, ruleset)` — both plain, deserialized data structures, no handles, no clients — and returns a decision document: for each review item, `waived(rule_id)` or `needs_signoff`, plus the overall verdict given a set of sign-off events (also passed in as data). The core performs no I/O, reads no clock, no environment, no randomness. If a rule needs "now" (e.g., waives with expiry), `evaluation_time` becomes an explicit pinned input recorded with the run — the clock is data, not ambient.

The shell does everything else: fetch the candidate, run validators, persist the snapshot, load the ruleset by hash, call the core, persist the decision, create workflow items, notify humans, promote the artifact. The shell is thin and dumb; all judgment lives in the core. Test the core with plain data fixtures (property tests work well here: "waiving is monotone in the ruleset," "decision is invariant under violation reordering"); test the shell with a handful of integration tests. Hexagonal architecture / ports-and-adapters is the structural version of the same idea if the core needs to be embedded in more than one shell (production orchestrator, local CLI, backtest harness — you'll want all three, and the CLI falls out for free).

One subtlety: canonicalize aggressively at the boundary. Sort violations by a stable key before hashing and before the core sees them, use canonical serialization (sorted keys, fixed number formatting), and avoid floats in rule predicates if you can. Iteration-order and serialization nondeterminism are the most common ways "pure" cores turn out not to be.

## Pinning: content-addressed vs. version-tagged

Use the git model: hashes are the truth, tags are mutable human-friendly pointers to hashes.

Content-address the immutable blobs — the frozen violation snapshot, the ruleset snapshot, the data artifact itself (or its manifest), and any reference/baseline data a rule consults. Content-addressing gives you integrity (you can verify a stored input wasn't mutated), deduplication, and makes "same inputs" a checkable proposition rather than a hope.

Version-tag the pointers — "rules current," "rules candidate," release names — and treat tag movement as the *release event* for rules. A merge to the rules repo should produce a new immutable ruleset hash; a separate, deliberate step moves the `current` tag. That decoupling is what gives you staging for free (problem 3): a ruleset can exist, be backtested, even shadow-run, before anything points `current` at it.

Then the evaluation record — the unit of reproducibility — is a small signed document: `{candidate_hash, violation_snapshot_hash, ruleset_hash, decision_core_version, evaluation_time, decision_hash}`. Note `decision_core_version`: you pinned data but reproducibility also needs the *code* identity, since the core's semantics are an input too. Given that record, anyone can re-derive the decision anywhere, and two records are comparable exactly when their input hashes match. One redundancy in your plan worth cleaning up: you list "a pinned rule version *and* a snapshot of the rules" as separate inputs — if rulesets are content-addressed, the pin *is* the snapshot reference; don't maintain both or they'll drift.

Which ruleset does a live candidate use? Bind it once, at evaluation start, by dereferencing `current` and recording the hash. If rules change mid-review, the candidate keeps its pinned ruleset; re-evaluating under the new rules is a *new* evaluation record for the same candidate, never an in-place mutation of the old one.

## Idempotency and the audit trail

Separate two kinds of writes, because they need opposite treatments:

**Facts (derived, recomputable).** Snapshots, decision documents, evaluation records. These are pure functions of their inputs, so give them *deterministic identities* derived from those inputs: the run ID is `hash(candidate, ruleset, core_version)`, the review item ID is a content hash of the violation group. Then writes are naturally idempotent PUTs: re-running produces the same IDs and either no-ops or overwrites with identical bytes. Prefer this over "check-if-exists-then-create," which has a race; a deterministic key plus put-if-absent (or compare-and-swap that verifies identical content) is the robust form. A nice side effect: if a re-run tries to write *different* content under the same ID, that's not a conflict to resolve — it's a determinism bug detector, and you should alarm on it.

**Acts (historical, never recomputed).** Human sign-offs, promotions, tag moves. These go in an append-only event log. They are not idempotent in the derived sense — they happened at a moment, by a person — but you make their *ingestion* idempotent with client-supplied dedup keys, and you never delete or rewrite them. The audit trail is this log, full stop.

The gate then becomes a pure fold: promotion is allowed iff, under the candidate's pinned evaluation record, every blocking review item is either waived by the decision document or matched by a sign-off event. Crucially, key sign-offs to the *content hash* of the review item, not a sequential row ID. That way a safe re-run reproduces the same item IDs and existing sign-offs reattach deterministically; sign-offs against sequential IDs would be orphaned by every re-run, which is exactly the collision you're suffering now.

## Ownership vs. projections

Apply the single-writer principle: every fact has exactly one owning component; everyone else consumes read-only projections. Concretely — the rules repo owns rulesets; the evaluation service owns snapshots and evaluation records; the sign-off service owns the event log; the promotion gate owns nothing, it's a pure query over the other three. Whatever dashboards or workflow tools exist today that also write "waived" or "approved" flags must be demoted to projections that render the log, or they will keep splitting the truth. You don't need full event sourcing for the whole system — that's overkill here — just the append-only log for acts plus rebuildable caches for facts. If a projection and the log ever disagree, the log wins and the projection is deleted and rebuilt; that rule is only enforceable if projections genuinely contain no facts of their own.

## Backtesting and rule staging

With pinned inputs this is almost trivial, which is why it's the right root cause to fix. A rules PR triggers CI that: loads the frozen violation snapshots of the last N candidates (or a curated regression corpus), runs the *candidate* ruleset through the same decision core, and diffs decision documents against the recorded ones. The diff is the review artifact: "newly auto-waived: 14 items (here they are), newly blocking: 2, unchanged: 3,401." Reviewers approve the *behavioral diff*, not the rule text — the same shift in review quality you get from snapshot tests. Add shadow mode for extra confidence: run the candidate ruleset alongside `current` on live evaluations for a week, log both decisions, alert on divergence, act only on `current`. Backtest catches regressions against history; shadow catches regressions against the present.

Two fidelity caveats. First, backtests are only as complete as your pinning — if any rule reads reference data that wasn't snapshotted per-candidate, historical replays silently use today's reference data and lie to you. Second, a backtest can't evaluate rules against violations that never occurred historically; keep a small synthetic fixture corpus for coverage of rare-but-important patterns.

## Where determinism isn't worth it

Your instinct about validators is correct, and it's worth naming why: freezing their output *moves the determinism boundary*. Downstream of the snapshot, everything is deterministic and reproducible; upstream, you only need the run to be *recorded*, not replayable. The gate, the audit story, and backtesting all operate on the snapshot, so bit-reproducible validators buy you nothing there. Do record validator versions/configs in the evaluation record anyway — that's cheap attribution, useful when a validator bug is discovered and you need to find affected candidates. And do watch validator *stability* operationally (same candidate, wildly different violation sets across runs erodes trust in the gate), but treat that as a quality metric, not an architectural requirement.

Other places to stop short of purity: don't chase deterministic *orchestration* (retry timing, parallelism order) — idempotent writes make orchestration nondeterminism harmless, which is much cheaper than eliminating it. And don't version-pin transitively into infrastructure (container digests, OS) unless an audit regime demands it; pinning data, ruleset, and core version covers the risks you actually have.

## On your terminology

Your three definitions are correct and worth keeping in the design docs — one refinement each. Determinism: your fix makes the *decision* deterministic; the end-to-end pipeline remains nondeterministic (validators), and that's fine because of the boundary-moving argument above — say "the decision is deterministic; the run is recorded," not "the system is deterministic." Reproducibility: it requires pinning code identity as well as data — a result is attributable to `(inputs, core version)`, not inputs alone. Idempotency: the deterministic-ID trick is what *connects* it to determinism — because facts are deterministic, they can have deterministic identities, which is what makes their writes idempotent; acts can't be, so they get dedup keys and append-only semantics instead. And your observation about problem 3 is exactly right: backtesting isn't a fourth property, it's the payoff — reproducibility is what turns "what would this rule change do?" from an experiment on production into a query over history.
