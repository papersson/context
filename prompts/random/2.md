# Infrastructure architectures for hosting AI agent workloads in production

## Method and evaluation axes

This survey treats an “agent session” as an **interactive, long-lived, tool-executing, per-user workspace** whose state includes at least: working directory changes, running processes, environment variables, network connections, and authentication context. The infrastructure problem is not “run code once”; it is “safely host a living workspace that is mostly idle, intermittently bursty, and difficult to migrate”. citeturn15view1turn10search0turn12view0

To compare architectures that all *work* but optimise different constraints, the report uses four core axes:

- **Isolation strength**: how hard it is for a compromised session to break out / pivot, and how strong the blast-radius boundary is (shared kernel vs user-space kernel vs VM kernel). gVisor explicitly positions itself as an “application kernel” (not a hypervisor), while Firecracker is a KVM-based microVM VMM with VM-grade isolation boundaries. citeturn1search35turn8view0turn5search1  
- **Lifecycle fidelity**: what “resume” really means (filesystem-only, process tree, full memory snapshot with CPU state). Fly’s suspend/resume and E2B’s pause/resume preserve “complete state” via snapshotting approaches; Modal more commonly relies on volumes + its own snapshot primitives rather than promising transparent process/memory resumption across sandboxes. citeturn9view8turn10search0turn12view0turn12view4  
- **Latency model**: cold start (new isolated environment) and warm start (restore from snapshot / pool). Firecracker’s own spec targets ≤125ms to guest `/sbin/init` under a minimal configuration, while real app cold starts are typically dominated by initialisation and image/build steps. citeturn8view0turn9view5turn17view0  
- **Operational complexity**: how much bespoke control plane you must build (scheduler integration, warm pools, snapshot stores, PVC orchestration, network policy, auditing). Kubernetes checkpoint/restore is explicitly “partially integrated” today, with the community standing up a dedicated working group in early 2026. citeturn13view2turn13view3turn13view0  

Throughout, “production-ready” is interpreted literally: features documented as stable in official docs, or clearly in active use by major platforms; anything described as alpha/beta/developer-preview is treated as **risk-weighted** even if promising. citeturn8view1turn12view4turn13view1

### What defines the emerging “agent compute” category

Across the platforms explicitly targeting agents, the differentiator is less “we run containers” and more **opinionated lifecycle & API design**:

- A first-class **session object** with methods like `exec`, file operations, port exposure, and identity scoping (agent-friendly control planes). citeturn12view0turn10search20turn8view8  
- Built-in strategies for **idle-heavy economics**: terminate-on-idle, stop-to-zero + restart, or suspend/resume from snapshots. Modal added explicit `idle_timeout` for Sandboxes; Fly Proxy can auto-suspend machines; E2B offers pause/resume and “auto-resume” patterns. citeturn12view0turn12view3turn9view8turn10search9  
- Strong emphasis on **untrusted execution boundaries**, because agents run semi-arbitrary code. Modal describes its sandbox boundary as gVisor-based; E2B describes Firecracker-based sandboxes and open-sources infra showing Firecracker usage. citeturn8view4turn9view1turn9view0turn9view4  

## Production architecture profiles

Each profile is organised as: isolation boundary → session lifecycle → burst/idle handling → sandboxing/security → notable implementation details you can reuse.

### Devin

**Isolation boundary.** Cognition’s docs describe a split architecture: a stateless “Brain” service in Cognition’s cloud and a per-session “Devbox” described as a “secure virtual environment”. The Enterprise SaaS model states: “Each Devin session runs on its own isolated machine”, and managed parallel Devins run “in [their] own isolated virtual machine”. citeturn15view4turn15view0turn15view2  

**Session lifecycle.** A session exposes an IDE (VS Code-like), shell, and browser, with logged command history and interactive takeover. This implies a long-lived workspace that preserves browser cookies and session data during the session (stateful browser context). citeturn15view1turn15view4  

**Burst/idle strategy.** Cognition explicitly includes controls to “put child sessions to sleep or terminate them”, hinting at a managed lifecycle control plane above per-session VMs (exact suspend mechanism not publicly specified). citeturn15view0turn15view2  

**Sandboxing and blast radius.** The “isolated machine/VM” boundary is stronger than shared-kernel multi-tenant containers in principle; the public docs stop short of specifying microVM vs full VM, snapshotting, or cold-start latencies. citeturn15view4turn15view0  

**Reusable pattern.** The “Brain + Devbox” split is a clean blueprint for enterprise deployments: keep orchestration/control-plane stateless and central, while pushing the risky tool execution into a per-session isolated compute cell that can be hosted in different network topologies (multi-tenant SaaS vs customer-dedicated VPC). citeturn15view4  

Conceptual structure:

```
User <-> Web UI/WS <-> Brain (stateless planner/controller)
                         |
                         v
                 Devbox (per-session isolated VM)
                 - shell / IDE / browser
                 - repo checkout + tools
```

### Copilot Workspace and Codespaces-backed execution

**Isolation boundary.** The Copilot Workspace user manual states its integrated terminal is “backed by a Codespace” and therefore a “secure sandbox with a full development environment installed”. GitHub’s Codespaces documentation describes Codespaces as a cloud development environment that “uses a container” for the dev environment. citeturn8view8turn8view9  

**Session lifecycle.** Copilot Workspace builds plans/diffs and then uses the Codespace-backed terminal for validation (build/lint/test), with the option to open the entire session in Codespaces. In other words: agent/planning UX and collaboration are separate from the actual tool-execution substrate (Codespaces). citeturn8view8  

**Burst/idle strategy.** Public docs in the provided sources do not specify suspend/hibernate semantics for Codespaces in the context of Copilot Workspace; operationally, you should assume “workspace start” is bounded largely by container start + any image pull/build steps, not by millisecond VM restore. citeturn8view9turn8view8  

**Sandboxing/security.** The practical boundary here is “per-codespace containerised dev env”, which is a good fit for *trusted* tool execution but is not as strong as microVM-per-session if you are executing arbitrary code at scale across tenants. The design is powerful for enterprise because environment configuration is standardised via devcontainer-like configuration, and the sandbox is integrated with repository access controls. citeturn8view9turn8view8  

Reusable blueprint:

```
Copilot Workspace UI/agent planner
    -> ephemeral Codespace (container-based dev env)
    -> run commands in terminal
    -> produce patch / PR
```

### Amazon Q Developer agent with sandboxed execution

**Isolation boundary.** Amazon’s engineering post describes a flow where the agent packages and uploads the project, then “initiates a sandbox instance or the customer specified docker container” for execution. It explicitly calls out “isolated, managed sandbox environment”. citeturn8view7  

**Session lifecycle.** The environment and allowed commands are driven by a **Devfile**: Amazon Q Developer supports a Devfile conforming to Devfile 2.2.0 schema and uses it to run `install`, `build`, and `test` commands. This is a key pattern: *environment reproduction + command allowlisting are first-class lifecycle inputs*, not ad-hoc agent decisions. citeturn8view7  

**Burst/idle strategy.** No explicit suspend/resume primitives are described; instead, the architecture leans on repeated “run commands → sync changes → provide feedback” iterations within the sandbox. The most important resource-efficiency lever here is likely “only start the sandbox when /dev is invoked” plus environment image optimisation (custom Docker images “preloaded with dependencies for faster startup”). citeturn8view7  

**Sandboxing/security.** Amazon emphasises: (a) execution is isolated; (b) environment is configured “without credentials to access non-public internet resources”; and (c) the command surface is curated/controlled via Devfile configuration. This is a strong, reusable security model for agent infra: **deny ambient credentials** + **explicit command surface** + **sandbox boundary**. citeturn8view7  

### Replit Agent and the snapshot-driven “transactional workspace” model

**Isolation boundary.** Replit’s infra post frames a “Repl” as a Linux container with a filesystem, running atop virtual machines. citeturn16view4  

**Lifecycle primitives.** Replit’s Snapshot Engine post describes three primitives that together resemble “agent compute” with rollback semantics:

- **Instant filesystem forks** via their Bottomless Storage Infrastructure (copy-on-write at block device level). citeturn16view0  
- **Versioned databases**: they run an unmodified local PostgreSQL whose data directory sits on the same versioned storage, enabling checkpoint/restore via manifest operations. citeturn16view2  
- **Isolated sandboxes + dev/prod split**: the agent is restricted to development databases, and users can revert changes to code or database state. citeturn16view0turn16view2  

**How their storage layer works (high-signal details).** The storage engine provides virtual block devices via NBD backed by Google Cloud Storage, lazily loaded and cached by storage servers co-located with compute. Disks are split into 16 MiB immutable chunks, and a manifest references chunk pointers for a version of the block device; copying a disk becomes “copy the manifest” (constant-time). citeturn16view0  

**Burst/idle strategy.** The post implies a cost model where you can create “fast, isolated forks” for agent experimentation and discard them, committing only useful deltas. This is an architectural alternative to process/memory hibernation: treat sessions as **transactional environments** with cheap copy/rollback, not necessarily long-lived running VMs. citeturn16view3  

Reusable blueprint for agent safety:

```
Base workspace (container + versioned disk + prod DB)
     |
     +--> fork workspace (CoW disk manifest) + fork dev DB manifest
             |
             +--> agent runs tools/tests, makes changes
             |
             +--> commit chosen result OR rollback/discard
```

### E2B and microVM-first agent sandboxes

**Isolation boundary.** E2B positions each sandbox as Firecracker-powered (“Each sandbox is powered by Firecracker”). The open-source infra repository explicitly states it provides “sandboxed execution environments using Firecracker microVMs”. citeturn2search23turn9view1turn9view0  

**Control plane / orchestration.** The infra repo describes self-hosting via Terraform across multiple clouds, and the internal doc indicates deployment on GCP using Terraform and Nomad. BYOC docs describe cluster components including an “Orchestrator” managing sandbox lifecycle and an “Edge Controller” routing traffic to sandboxes and proxying cluster control calls. citeturn9view0turn9view1turn9view3  

**Lifecycle primitives.** E2B offers both:

- **Pause/Resume** (“sandbox persistence”) that preserves filesystem *and memory* state, including running processes and loaded variables/data. citeturn10search0  
- **Snapshots** as a one-to-many checkpoint: create a snapshot of filesystem+memory, then spawn many new sandboxes from it; the original continues after being briefly paused. Active connections may drop during snapshot, requiring clients to reconnect. citeturn9view9turn8view3  

It also documents “auto-resume” semantics (a paused sandbox can later be resumed, and will pause again on timeout; killing permanently deletes it). citeturn10search9  

**Agent-facing execution surface.** E2B’s infra includes an `envd` daemon “running inside a sandbox” to support SDK calls (i.e., a guest agent responsible for executing commands and mediating filesystem/process operations). citeturn10search14turn9view1  

**Economics.** Pricing is explicitly per-second of a running sandbox, with separate CPU/memory line items. This matters for idle-heavy sessions: unless pause/resume is used aggressively, you pay wall-clock. citeturn9view2turn10search0turn10search2  

**Open-source availability.** The orchestration/infrastructure is open-sourced (Apache-2.0) and includes a self-hosting guide; BYOC is documented but positioned as enterprise. citeturn9view0turn9view3  

### Modal Sandboxes and gVisor-based isolation

**Isolation boundary.** Modal’s sandbox networking/security docs state: “Sandboxes are built on top of gVisor… giving you stronger isolation than standard runc containers.” This is explicitly a syscall-interception / user-space-kernel model rather than per-sandbox VM kernels. citeturn8view4turn1search35  

**Lifecycle primitives.** Modal’s Sandbox docs specify:

- Default maximum lifetime of 5 minutes, configurable up to 24 hours via `timeout`. citeturn12view0  
- Optional `idle_timeout`: terminate after a period of inactivity, with activity defined by running commands, stdin writes, or open tunnel TCP connections. citeturn12view0turn12view3  
- Advice to use “Filesystem Snapshots” for state preservation across longer horizons (the details of those snapshots are outside the captured excerpt, but the lifecycle recommendation is clear). citeturn12view0  

**State and storage.** Modal supports persistent Volumes and CloudBucketMounts. It notes that Volume file syncing differs: files created inside the sandbox sync back when the sandbox terminates (unless you explicitly `sync` for Volumes v2). Volumes v2 are beta and carry explicit cautions about mission-critical data. citeturn12view1turn12view4  

**Economics and scaling posture.** Modal’s pricing page emphasises “you never pay for idle resources — just actual compute time, by the CPU cycle,” with per-second CPU/memory rates and explicit concurrency limits by plan tiers. This is aligned with bursty agent workloads if your agent runtime can truly go idle (and tear down) without needing full-fidelity in-memory resumption. citeturn12view2  

### Fly Machines and snapshot-backed suspend/resume

**Isolation boundary.** Fly’s architecture docs state: application code runs in Firecracker microVMs; Fly emphasises strong hardware-virtualisation-based isolation and notes an effort to avoid CPU steal via best-effort resource dedication. citeturn9view4turn5search1  

**Lifecycle primitives.** Fly has an explicit **suspend/resume** feature: suspend captures complete VM state (CPU registers, memory contents, open file handles) via Firecracker snapshots; resume restores from snapshot rather than cold boot. Typical performance is “a few hundred ms” resume and “~2+ seconds” cold start for common apps. citeturn8view2turn9view8  

**Scale-to-zero.** Fly Machines were designed to support workloads that “scale to zero”, with the proxy able to boot machines for you and shut them down when idle; autosuspend via Fly Proxy can be configured (`auto_stop_machines = "suspend"` and `auto_start_machines = true`). citeturn9view5turn8view2  

**Operational model.** Fly Machines are managed via a REST API and are described as booting instances in about ~300ms (in Fly’s own blog). This is near the microVM substrate-level latency, but real workloads may still be gated by application initialisation. citeturn9view5turn8view0  

### CodeSandbox VM Sandboxes and “clone-by-snapshotting” as a population-scale pattern

**Isolation boundary.** CodeSandbox describes VM Sandboxes as running on VMs and leveraging memory snapshotting for fast start/resume. Their engineering post explicitly uses Firecracker microVMs and Firecracker snapshotting (state file + memory file). citeturn17view1turn17view0turn8view1  

**Lifecycle primitives and performance claims.** The engineering post provides unusually concrete numbers:

- Snapshot files: one for configuration and one for memory; memory snapshot size scales with VM memory (e.g., 4 GB memory → 4 GB file). citeturn17view0turn8view1  
- Resume uses `mmap`, loading only what’s needed; they report resume timings ~200–300ms and show an internal benchmark where “memory snapshots” bring a “time to running preview” down to ~0.6s from tens of seconds/minutes under other caching schemes. citeturn17view0  

**Fork-as-clone.** The docs and blog describe cloning a running environment as the core workflow: “fork within 2 seconds” and “spin up an environment in 1.5 seconds” using memory snapshotting. citeturn17view1turn17view0  

**Why this matters for agents.** CodeSandbox’s architecture is effectively an existence proof that (a) VM snapshotting can be pushed into user-facing interactive latency budgets, and (b) copy-on-write + snapshot stores can support massive fanout of “stateful sessions” without keeping everything hot. That is directly analogous to agent sessions that are mostly idle but need instant resumption. citeturn17view0turn8view1  

### Docker Sandboxes and local microVM isolation for coding agents

**Isolation boundary.** Docker’s Jan 2026 post describes Docker Sandboxes as moving to “microVM isolation” on macOS and Windows, where “each agent runs inside a dedicated microVM” and only the project workspace is mounted. It explicitly aims to prevent host damage while permitting unattended agent operation. citeturn18view0  

**Lifecycle primitives.** The key lifecycle feature is “fast reset”: delete a sandbox and spin up a fresh one quickly. Docker also emphasises that the agent can build and run Docker containers **inside** the microVM without access to the host Docker daemon (a hard-earned security constraint for agent toolchains). citeturn18view0  

**Why it matters for production architectures.** Even if you do not deploy Docker Sandboxes server-side, it demonstrates a robust pattern for “agent compute” at the edge: push tool execution to a local microVM boundary, mount only the workspace, and expose audited network allow/deny controls. citeturn18view0  

### Remote dev platforms as headless agent infra

#### Coder

Coder workspaces are designed to start/stop and can be automatically stopped via inactivity timeouts configured by templates. The workspace lifecycle docs describe stop/resume semantics and that deleting runs `terraform destroy`, emphasising that templates are control-plane definitions rather than mere container images. citeturn3search12turn3search0  

For agents, this maps cleanly onto “per-session isolated workspace + persistent resources,” but you must still decide (and implement in templates) whether the underlying workspace is a Kubernetes pod, a VM, or something microVM-based.

#### DevPod

DevPod describes a workspace as stoppable/restartable “without losing its state”, with provider-specific behaviour: it can stop underlying VMs in cloud providers or terminate containers for non-VM providers. Auto-inactivity timeout is built in, including semantics like “preserve data and state” on restart for machine providers. citeturn3search25turn3search1turn3search9  

As an agent substrate, DevPod is attractive when you want the devcontainer ecosystem and multi-provider abstraction, but it is not a turnkey multi-tenant sandbox boundary by itself; you will still need strong per-session security controls (network, credentials, syscall boundary).

#### Gitpod and Eclipse Che

Gitpod’s workspace lifecycle documentation spells out persistence constraints (e.g., “only files and directories inside `/workspace` are preserved”). Eclipse Che exposes configurable workspace idle timeout and start timeout fields in its CheCluster CRD schema. These are directly relevant knobs for agent session economics, but (again) they are not full-fidelity “hibernation”; they are workspace stop/start semantics with persisted volumes. citeturn3search10turn3search11

### Scaling patterns for 20, 100, 500 concurrent sessions

The right architecture depends less on raw concurrency and more on **how many sessions must be “ready-to-act” within sub-second latency** versus “can wait seconds”. The most reusable productivity insight from Fly and CodeSandbox is: if you can *actually* suspend and resume VM state, you can scale “warm capacity” by storing snapshots, not running processes. citeturn8view2turn17view0turn8view1  

Below is a modelling framework (not a benchmark claim): it shows how to reason about density on a 64-core / 256GB node using documented overhead primitives.

**Overhead anchors you can safely use:**

- Firecracker VMM threads overhead target ≤5 MiB for a microVM running 1 vCPU / 128 MiB RAM (excluding guest RAM). citeturn8view0  
- VM snapshot memory file is size ≈ guest memory (e.g., 4 GB VM → 4 GB snapshot file). citeturn17view0  
- Fly: resume from suspend “few hundred ms”; cold start “~2+ seconds for common apps”. citeturn8view2  
- CodeSandbox: resume ~200–300ms; cloning uses snapshotting and CoW techniques. citeturn17view0  

**Pattern tradeoffs (qualitative + anchored numbers):**

- **Shared “fat” container with process-level isolation**: maximum density, but weakest boundary (shared kernel + same container namespace if misconfigured). Viable only for trusted code and strong in-process sandboxing; typically not acceptable for multi-tenant untrusted agent execution. citeturn1search35turn18view0  
- **Per-session containers with warm pools**: good default on Kubernetes; cold start can be excellent with pre-pulled images, but “resume” is typically filesystem-only (PVC) unless you build checkpoint/restore (still emerging). citeturn4search3turn13view2turn3search11  
- **Per-session microVMs + snapshot/restore**: best boundary and best “true warm resume”, but you pay in snapshot storage and microVM operational complexity; in return you can keep hundreds of sessions “near-zero compute” while still resuming in sub-second. citeturn8view2turn8view1turn8view0turn17view0  
- **Serverless container platforms**: good burst scaling, but often mismatch on “deeply stateful resume” unless you build your own snapshotting/restore or accept rehydration costs (re-clone, re-install, re-run). The Modal model is closer to “pay per compute cycle” + use volumes/snapshots for continuity rather than trying to preserve full process state. citeturn12view0turn12view2turn12view4  

## Architecture recommendation tiers

Each tier is presented as a deployable blueprint for 5–500 concurrent sessions, with explicit tradeoffs.

### Tier one self-hosted Kubernetes with standard primitives

This is “no microVM runtime, minimal bespoke infra”.

**Core idea.** Per session = one Pod + one PVC + one narrowly-scoped ServiceAccount. “Suspend” = stop pod after inactivity; “resume” = recreate pod mounting same PVC. Your agent runtime must tolerate losing process state and must reattach to filesystem-only continuity. citeturn3search11turn3search10turn4search11  

**Components.**

- Session Manager (your service): creates a Session CR (or directly creates Pod/PVC) and maintains a WebSocket channel to the user.
- Workspace Pod: agent runner + tool executors; attach `/workspace` PVC; read-only shared volumes for base repos/config.
- Queue/Scaler: KEDA scales “agent worker” pods from 0 based on session queue depth; your long-lived sessions are separate pods not subject to scale-to-zero. citeturn4search3turn4search11  

**Lifecycle.**

1. Create PVC (per session) + Pod.  
2. Agent runs; tool execution occurs inside the pod.  
3. On idle (no WS activity / no running command), terminate pod; keep PVC.  
4. Resume by recreating pod attaching same PVC; agent rehydrates context from filesystem and stored conversation state.

**Tradeoffs accepted.** You sacrifice **process/memory continuity** to preserve **operational simplicity**. This works if your agent is designed to checkpoint its own state (conversation + task plan + “what’s running”) and can restart tools deterministically.

### Tier two self-hosted Kubernetes with sandboxed runtimes and workspace orchestration

This is “moderate investment: better isolation, better workspace lifecycle, still mostly Kubernetes-native”.

**Core idea.** Keep Pods as the scheduling unit, but upgrade isolation and workspace tooling:

- Use gVisor (user-space kernel) or Kata (VM-backed) as the runtime class depending on your threat model and performance tolerance. citeturn1search35turn4search6turn7search2turn7search4  
- Adopt workspace-centric patterns from remote dev platforms: configurable idle timeout, start timeout, PVC strategies (per-user/per-workspace), and template pipelines. Eclipse Che exposes these knobs explicitly in its CRD schema; DevPod and Coder document start/stop lifecycle controls and defaults. citeturn3search11turn3search12turn3search25turn3search1  

**Lifecycle improvements.** You still don’t get “true hibernation” easily, but you get stronger sandboxing and better lifecycle automation.

**What you build.**

- A Session CRD + controller that:
  - Creates PVC, Pod (with runtimeClassName = gVisor/Kata), NetworkPolicy, and per-session ServiceAccount.
  - Enforces idle timeout by separate controller logic (because Kubernetes itself doesn’t yet “hibernate pods” as a first-class primitive). citeturn13view2turn4search3  

**Tradeoffs accepted.** You accept the complexity of sandboxed runtimes and per-session policy objects (NetworkPolicy, PSA, seccomp/AppArmor), but still accept that resume is mostly “restart with disk state” rather than full memory restore.

### Tier three microVM-first agent compute with snapshot-backed suspend/resume

This is “ideal architecture” when you can run microVMs (cloud or on-prem), and are willing to invest in a dedicated control plane.

**Core idea.** Per session = microVM (Firecracker-class) with:

- A guest agent (envd-style) exposing exec/files/ports APIs to your session manager. citeturn10search14turn9view3turn9view1  
- Snapshot-backed suspend/resume for idle periods (Fly’s model) or clone-by-snapshotting for fast fork (CodeSandbox’s model). citeturn8view2turn17view0turn8view1  

**Referenceable primitives.**

- Firecracker boot target ≤125ms to `/sbin/init` under minimal conditions; VMM overhead target ≤5 MiB for a tiny microVM baseline. citeturn8view0  
- Snapshot API supports pause → create snapshot → resume; Firecracker documents snapshot format versioning and notes diff snapshots are “developer preview”. citeturn8view1  

**Production-proven patterns to borrow.**

- Fly: suspend/resume uses Firecracker snapshots and delivers “few hundred ms” resume, while cold starts are ~2+ seconds for common apps. citeturn8view2turn9view4  
- CodeSandbox: treat the microVM state itself as a clonable artifact; use CoW and memory snapshotting to fork quickly and avoid reinitialisation costs. citeturn17view0turn17view1  
- E2B BYOC: separate edge routing/control from orchestrator nodes; store templates/snapshots/logs inside the customer VPC; send anonymised metrics to control plane. citeturn9view3turn9view1  

**How to self-host the substrate.** If you need an open stack:

- firecracker-containerd provides an OSS approach to manage Firecracker microVMs via containerd, with a control plugin, runtime shim, and in-guest agent that invokes runc to spawn containers inside the microVM. citeturn9view6  

**Tradeoffs accepted.** You accept the operational complexity of microVM orchestration (kernels, images, snapshot stores, network identity, observability), in exchange for the only broadly demonstrated way to make **idle-heavy sessions cheap** *without sacrificing in-memory/process continuity*.
