# Validating interconnected entities: patterns from GIS, game engines, and enterprise systems

Systems managing complex entity relationships have evolved sophisticated validation approaches far beyond schema checks. The **core insight** across GIS, game engines, ERP, and graph databases is that validation must be architectural—embedded in transaction boundaries, query systems, and propagation mechanisms rather than scattered across procedural code. Three patterns dominate: **constraint triggers with deferred evaluation** (allowing multi-entity changes before validation), **query-based filtering** (letting the runtime exclude invalid entity combinations), and **aggregate boundaries** (treating related entities as atomic consistency units).

This report catalogs validation patterns, transformation safety mechanisms, constraint discovery techniques, and testing strategies drawn from PostGIS topology, Unity ECS, SAP RAP, Neo4j, and Domain-Driven Design.

## Pattern catalog: validation approaches for interconnected entities

### Deferred constraint triggers handle multi-entity consistency

PostGIS demonstrates the most elegant pattern for validating interconnected spatial entities: **deferrable constraint triggers** that evaluate at transaction commit rather than row-by-row. This allows temporary inconsistency during a transaction while guaranteeing consistency at boundaries.

```sql
CREATE CONSTRAINT TRIGGER noded_road
  AFTER INSERT OR UPDATE ON roads 
  DEFERRABLE INITIALLY DEFERRED  -- Validates at COMMIT, not per-row
  FOR EACH ROW EXECUTE FUNCTION noded_road_trigger();

BEGIN;
SET CONSTRAINTS ALL DEFERRED;
INSERT INTO roads VALUES (5, 'LINESTRING(4 0, 6 0)');
INSERT INTO roads VALUES (6, 'LINESTRING(2 2, 4 0)');  -- References first road
COMMIT;  -- Both validated together
```

This pattern directly addresses "constraint chaining"—changing field A that requires B and C to also change. By deferring validation, you can make all related changes within a transaction before consistency checks fire.

### Query-based validation filters invalid entity combinations automatically

Unity ECS and game engines take a fundamentally different approach: rather than validating entities exist in valid states, they **filter which entities systems can operate on** using declarative queries. This eliminates entire classes of validation code.

```csharp
EntityQuery query = new EntityQueryBuilder(Allocator.Temp)
    .WithAll<Health, Position>()      // Required: entity must have both
    .WithAny<PlayerTag, EnemyTag>()   // Optional: at least one
    .WithNone<DeadTag>()              // Exclusion: must not have
    .Build(this);
```

The **WriteGroup pattern** handles mutually exclusive components—"if component X exists, certain rules apply instead of default rules." Systems declare which components they write to, and queries can filter to entities where only specific WriteGroup members exist.

### Aggregate boundaries enforce cross-entity invariants transactionally

Domain-Driven Design aggregates represent the **strongest form** of interconnected entity validation. The aggregate root mediates all access to internal entities, ensuring invariants across the cluster remain valid after every operation.

Key mechanisms:
- **Root-mediated access**: External code touches only the aggregate root, never internal entities
- **Single transaction scope**: All entities within an aggregate save or fail atomically
- **Reference by ID**: Aggregates reference other aggregates by ID only, not by containment—preventing unbounded consistency requirements

The critical principle: if a business rule must be immediately consistent, the participating entities belong in the same aggregate. Rules that can tolerate eventual consistency span aggregates via domain events.

### Graph databases combine schema constraints with pattern-based validation

Neo4j provides layered validation: **schema-level constraints** (uniqueness, existence, type) plus **Cypher pattern queries** for complex relationship rules that can't be expressed declaratively.

```cypher
-- Schema constraint: isbn must exist on all Book nodes
CREATE CONSTRAINT FOR (n:Book) REQUIRE n.isbn IS NOT NULL

-- Pattern validation: find orphaned orders referencing missing products
MATCH (o:Order)-[:REFERENCES]->(p:Product)
WHERE p IS NULL
RETURN o.orderId AS brokenReference
```

The **index-free adjacency** model means multi-hop validation queries perform consistently regardless of dataset size—validating 3-hop relationship chains runs in constant time per traversal.

## Transformation safety: ensuring mutations preserve constraints

### Pre-check, execute, post-validate pattern

SAP RAP formalizes the transformation validation lifecycle with distinct phases:

1. **Precheck**: Fast validation before expensive operations—catches obvious violations early
2. **Determination**: Auto-calculations that run when trigger conditions are met (like database triggers)
3. **Validation on save**: Comprehensive consistency check against full business rules
4. **Commit**: Only after all validations pass

```abap
define behavior for ZI_Travel
  validation validateCustomer on save { create; field CustomerID; }
  validation validateDates on save { create; field BeginDate, EndDate; }
  determination calcTotal on save { create; field LineItems; }
```

The **field-triggered validation** is particularly powerful: validations only fire when specific fields change, avoiding redundant checks.

### Dirty area tracking for incremental validation

ArcGIS geodatabase topology uses **dirty areas**—regions marked for re-validation after edits. Rather than re-validating the entire dataset, only features within the dirty area are checked:

1. Edit creates/modifies dirty area covering change extent
2. Validation scans only dirty area against topology rules
3. Errors generated for violated relationships
4. Fixes applied (automatic or manual)
5. Re-validate to confirm resolution

This pattern enables **incremental constraint checking** on large datasets where full validation would be prohibitively expensive.

### EntityCommandBuffer for structural changes

Unity ECS requires **deferred entity modification** because structural changes (adding/removing components) can't happen during system iteration. The EntityCommandBuffer collects changes and applies them at sync points:

```csharp
var ecb = new EntityCommandBuffer(Allocator.TempJob);
ecb.AddComponent(childEntity, new Parent { Value = parentEntity });
ecb.Playback(EntityManager);  // Changes applied, hierarchy systems update
```

This ensures parent-child relationships and component dependencies update atomically rather than leaving entities in intermediate invalid states.

### Cascading referential actions

Oracle provides declarative transformation cascading through foreign key actions:

| Action | Behavior |
|--------|----------|
| CASCADE DELETE | Delete dependent rows when parent deleted |
| SET NULL | Set foreign key to NULL when parent deleted |
| DEFERRED | Check constraints after statement completes, not per-row |

The **deferred constraint checking** is essential for self-referential updates where rows reference each other within a single statement.

## Constraint discovery: extracting implicit rules from code

### Dynamic invariant detection with Daikon

**Daikon** observes runtime variable values and generalizes patterns into likely invariants. It instruments code to record values at program points, then hypothesizes constraints that held across all observations:

- Constant values: `x = a`
- Range constraints: `a ≤ x ≤ b`
- Linear relationships: `y = ax + b`
- Containment: `x ∈ y`
- Ordering: `x ≤ y`
- Structural: `lst.next.prev = lst`

The DYNAMATE approach combines Daikon with mutation-based test generation, achieving **97% proof obligation discharge** on java.util methods—demonstrating that dynamic detection combined with mutation testing can surface most implicit constraints.

### Event Storming for collaborative discovery

**Event Storming** (Alberto Brandolini) is a workshop technique that surfaces implicit constraints through domain expert collaboration:

1. Storm domain events (orange stickies): past-tense descriptions of what happened
2. Identify commands (blue): user intents triggering events
3. Define aggregates (yellow): group related events and commands
4. Mark policies/processes (purple): business reactions to events
5. Mark **hotspots** (red): ambiguities, conflicts, implicit rules to resolve

The hotspots directly identify validation rules that exist as tribal knowledge but aren't documented.

### Static analysis and program slicing

For extracting constraints from existing procedural code:

- **Backward slicing**: From a variable, find all statements affecting its value
- **Forward slicing**: From a statement, find all affected statements
- **Variable classification**: Track how business data flows through code

Commercial tools like **AveriSource** and **EvolveWare Intellisys** use AI to extract business rules from legacy systems, separating business logic from implementation.

### Migration from implicit to explicit constraints

The practical migration path:

1. Run Daikon on existing code with diverse inputs
2. Review detected invariants with domain experts
3. Convert validated invariants to declarative specifications
4. Add property-based tests to verify constraint enforcement

Target formats include Bean Validation annotations, Pydantic models, or database constraints—anything that makes the rule discoverable and testable.

## Testing strategies for relationship-dependent validation

### Property-based testing with constrained generators

Hypothesis and QuickCheck support **composite strategies** for generating valid interconnected test data:

```python
@st.composite
def entity_with_relationships(draw):
    parent = draw(parent_strategy())
    children = draw(st.lists(
        child_strategy(parent_id=parent.id),
        min_size=1  # Constraint: must have children
    ))
    return EntityGraph(parent, children)
```

The `@composite` decorator allows dependent draws—generating child values based on already-generated parent values. This is essential for referential integrity in test data.

### Builder pattern for test fixtures

The Builder pattern provides domain-specific interfaces for creating complex test objects with relationships:

```java
public class MechanicBuilder extends BaseBuilder<Mechanic> {
    public MechanicBuilder withCars(int count) {
        this.entity.cars = IntStream.range(0, count)
            .mapToObj(i -> new CarBuilder().build())
            .toList();
        return this;
    }
    
    public MechanicBuilder onHoliday() {
        this.entity.ptos = List.of(new PtoBuilder().forMechanic(this.entity).build());
        return this;
    }
}
```

This pattern **encodes relationship constraints in the builder API** rather than requiring test authors to remember them.

### Mutation testing validates constraint coverage

Mutation testing evaluates whether tests actually verify validation logic by introducing small code changes and checking if tests catch them:

| Mutation | Example |
|----------|---------|
| Value | `age >= 18` → `age >= 16` |
| Operator | `&&` → `\|\|` |
| Statement | Remove `if` branch |

A surviving mutant in validation code means **no test verifies that specific constraint**. PIT (Java), Stryker (JavaScript), and Muter (Swift) are the primary tools.

### Contract testing for transformation boundaries

Consumer-Driven Contract (CDC) testing ensures transformations meet consumer expectations:

```groovy
Contract.make {
    request {
        url "/entity/1/transform"
        method POST()
        body(operation: "merge", targetId: 2)
    }
    response {
        status OK()
        body(id: 1, mergedFrom: [2], constraints: ["valid": true])
    }
}
```

Pact and Spring Cloud Contract enable providers to verify contracts independently of consumers, catching constraint violations at service boundaries.

## Case studies: systems with similar validation challenges

### PostGIS topology: cadastral parcel management

Land administration systems manage parcels that must not overlap, share boundaries exactly, and maintain containment hierarchies (parcels within municipalities within states). PostGIS addresses this through:

- **Topology primitives**: Nodes, edges, and faces stored with explicit adjacency pointers
- **TopoGeometry**: Features defined by topology primitive references rather than coordinates
- **ValidateTopology()**: Returns specific errors (invalid next_left_edge, orphan nodes)
- **Deferred triggers**: Allow batch parcel updates before boundary validation

When a surveyor updates a parcel boundary, the topology module automatically updates adjacent parcels sharing that boundary—a form of built-in constraint chaining.

### Unity ECS: game entity validation

Games manage entities with complex component dependencies: a "Renderable" entity requires Transform and Mesh components; a "PhysicsBody" requires Collider and RigidBody. Unity addresses this through:

- **Aspect types**: Bundle required/optional component declarations
- **RequireForUpdate**: Systems skip execution if required components don't exist
- **LinkedEntityGroup**: Ensures parent-child entity lifetimes are synchronized
- **ICleanupComponent**: Tracks previous state for detecting orphaned references

The pattern of **declaring dependencies in type definitions** rather than validating at runtime shifts constraint enforcement from scattered procedural checks to centralized, compilable specifications.

### SAP RAP: business object transactions

ERP transactions span interconnected business objects—a sales order affects inventory, accounts receivable, revenue recognition, and shipping. SAP RAP manages this through:

- **Behavior definitions**: Declarative specifications of validations and determinations
- **BAPI return parameters**: Structured error reporting with automatic rollback on failure
- **Object dependencies**: Centralized management of inter-entity constraints (transaction CT04)
- **Two-layer validation**: Frontend validations for fast feedback, backend validations as mandatory consistency gates

The **determination** concept—automatic calculations triggered by field changes—directly implements constraint chaining at the framework level.

## Constraint chaining patterns across systems

The research reveals three dominant approaches to "changing field A requires changing B and C":

| Pattern | Implementation | Used By |
|---------|---------------|---------|
| **Deferred evaluation** | Collect all changes, validate at transaction boundary | PostGIS, Oracle |
| **Determination triggers** | Auto-calculate dependent fields on change | SAP RAP, ArcGIS |
| **Topological editing** | System identifies shared vertices, updates all affected features | QGIS, PostGIS Topology |

The key insight: **constraint chaining should be automatic**, handled by the framework rather than requiring developers to remember which fields are coupled. This is achieved through topology primitives (GIS), component systems (games), or determination rules (ERP).

## Recommendations for procedural validation systems

Based on patterns from these systems:

1. **Move constraints to transaction boundaries**: Use deferred triggers or commit-time validation rather than per-statement checks
2. **Declare dependencies in types**: Like Unity Aspects or SAP behavior definitions, make constraints discoverable through type definitions
3. **Implement dirty area tracking**: Only re-validate affected regions after changes, not entire datasets
4. **Use dynamic detection for discovery**: Run Daikon or similar tools on existing code to surface implicit constraints
5. **Adopt property-based testing**: Composite strategies generate valid interconnected test data by construction
6. **Consider aggregate boundaries**: Group entities that must be immediately consistent; handle cross-aggregate rules via eventual consistency

The systems with the most maintainable validation share a common trait: constraints are **declarative, centralized, and automatically enforced** rather than scattered across procedural implementations.
