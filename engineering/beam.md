# The BEAM: fault tolerance as a runtime property

This document is a worked instance of one idea: what actually makes the Erlang BEAM good at staying up, and why that quality lives in the runtime rather than in any API you could copy. It hangs under [dependability.md](./dependability.md) as one exemplar in the fault-tolerance branch. Read that document for the umbrella theory (attributes, threats, means) and the cross-cutting patterns this one draws on; read this one for the concrete telling.

## 1. The question

There is a reductive line you hear whenever the actor model comes up: "actors are just locks own data." The claim is that an actor is nothing more than some mutable state plus a lock, with the lock made implicit by forcing all access through a message queue. By that reading the BEAM offers no new capability, only a rearranged syntax for mutual exclusion, and you could reproduce the whole thing in any language with threads and a queue.

The reductive line is half right, which is what makes it worth taking seriously. An actor genuinely does relocate the lock: instead of writing `lock(); mutate(); unlock()` around the state, you put the state inside an execution unit that processes one message at a time, and the serialization falls out for free. That part is real and we will make it precise (it is rung 4 of the ladder below).

What the line misses is everything that makes the serialization a *guarantee* rather than a *convention*. "Locks own data" describes a programming discipline you can follow or forget. The BEAM's value is that several of these properties are enforced by the runtime and cannot be forgotten, opted out of, or leaked around, because the language gives you no way to express the violation. The question this document answers is precisely which properties those are, which ones a library can reproduce, and which ones structurally cannot be reproduced outside the runtime that enforces them.

The short answer: the BEAM's payoff is a fault-containment guarantee, and that guarantee is manufactured by mechanically enforced state isolation. Porting the actor API gives you the shape of the thing without the enforcement, which means without the guarantee. The rest of this document builds that claim one rung at a time, then tests it against Akka as a counter-example.

## 2. Vocabulary

Define these before going further; the ladder in section 3 uses each term as a load-bearing primitive.

**Execution unit.** An independently schedulable sequence of instructions. This is the genus; thread, BEAM process, actor, fiber, and goroutine are species of it. "Independently schedulable" means a scheduler can run it, suspend it, and resume it on its own, separate from other execution units.

**Scheduler.** The component that decides which execution unit runs next on a given CPU, and that suspends a running unit so another can have the CPU. An OS kernel has a scheduler over threads; the BEAM has its own scheduler over BEAM processes, typically one scheduler thread pinned to each CPU core.

**Preemption unit.** The granularity at which a scheduler can *forcibly* suspend a running execution unit, without that unit's cooperation. "Forcibly" is the operative word: cooperative suspension (a unit voluntarily yielding) is not preemption. For an OS, the preemption unit is the OS thread, and the forcing mechanism is the timer interrupt: hardware fires an interrupt on a fixed schedule, the kernel takes control, and it can suspend whatever was running. For the BEAM, the preemption unit is the BEAM process, and the forcing mechanism is reduction exhaustion (defined below).

**BEAM process.** A lightweight execution unit living inside the Erlang VM. It is not an OS process and not an OS thread. A freshly spawned BEAM process costs a few hundred bytes, and a single VM routinely holds millions of them. The defining structural fact, the one everything else leans on: each BEAM process has its **own private heap**. Nothing it allocates is visible to any other process. (OS process is the contrasting term: an OS-level address space with its own page tables, costing kilobytes to megabytes and managed by the kernel. BEAM processes are cheaper than OS threads by orders of magnitude, which is the whole point of section 8.)

**Reduction.** The BEAM's unit of work for scheduling, roughly one function call. Each process is handed a budget of reductions when it is scheduled onto a core. Every function call decrements the budget. When the budget hits zero (reduction exhaustion), the scheduler forcibly suspends the process and picks another, regardless of what the process was doing. This is **reduction counting**, and it is the BEAM's preemption mechanism: it yields per-process fairness that no user code can defeat, because the counting happens below the level user code can reach. A process cannot monopolize a core by running a tight loop, the way a thread in a cooperative system can, because the loop spends reductions and gets suspended like everything else.

With these five terms in hand, the ladder.

## 3. The ladder of properties

The properties stack. Each rung is stated using only terms from earlier rungs, so the dependencies are explicit and you can see exactly which lower property each higher one rests on.

**Rung 0: the process.** The unit of structure is the BEAM process: a few hundred bytes, spawned in microseconds, with its own private heap. Because it is this cheap, the process is the *default* unit of program decomposition. You spawn one per request, per connection, per session, per protocol state machine, without thinking about the cost. This is the precondition for everything else, because the later guarantees are only useful if you can afford to wrap every concurrent activity in its own process. If processes cost what OS threads cost, you would ration them, and the containment story would apply only to a handful of coarse units.

**Rung 1: preemptive scheduling.** The scheduler preempts processes by reduction counting (section 2). No process can starve another by running too long, because the runtime forcibly suspends it at reduction exhaustion. This rung uses only rung 0 (there must be processes to schedule). It buys per-process fairness with no cooperation required from user code: a buggy or hostile process that loops forever is suspended and resumed like any other, and the rest of the system keeps running.

**Rung 2: state isolation (shared-nothing).** Because each process has its own private heap (rung 0) and the language provides no construct for one process to reference another's heap, processes share no mutable memory. This is **shared-nothing**, also called **state isolation**: a property of *memory*, that execution units have no mutable memory in common. It is not a discipline the programmer maintains; it is a fact about what the language can express. There is no syntax for "a pointer into another process's heap," so the violation is not available to write down. Two consequences fall out immediately. Garbage collection is per-process: each process collects its own small heap independently, so there is no stop-the-world pause across the system, and GC latency is bounded by one process's heap size rather than the whole VM's. And, the load-bearing consequence for rung 5: if processes share no mutable state, then one process's corruption cannot be another process's corruption. This rung uses rung 0 (private heaps) and is the structural heart of the whole document.

**Rung 3: message passing by copy.** Since processes share no memory (rung 2), they communicate by sending messages, and a message is **copied** from the sender's heap into the receiver's heap. The copy is the cost that buys the isolation. You pay copy bandwidth and extra memory on every message, and in exchange the sender and receiver remain genuinely independent: after the send, there is no shared object that both can mutate, because the receiver holds its own copy. This rung uses rung 2 (there is no shared memory, so a reference would be meaningless; copying is the only coherent option). The cost is real and section 10 returns to it.

**Rung 4: serialized state access.** A process handles its messages one at a time, pulling the next from its mailbox only after finishing the current one. So the state living inside a process is accessed serially: no two manipulations of it ever interleave, because there is only one thread of control inside the process and it is busy with one message at a time. This is the rung the reductive "locks own data" line correctly identifies. It is equivalent to a critical section under a fair mutex: the state is protected, accesses are mutually exclusive, and fairness comes from rung 1. The difference from an explicit lock is that **you cannot forget to lock**, because the only door into the state is the mailbox, and the mailbox serializes by construction. The actor model relocates the lock from *code* (a `lock()` call you must remember to write around every access) to *state* (the state sits inside a process whose mailbox is the only entrance). This rung uses rung 3 (messages arrive in the mailbox) and rung 1 (fairness in handling them). Note what it does *not* use: rung 4 alone does not require rung 2. You can serialize access to state without isolating that state from everyone else. Hold that thought; it is exactly where Akka and TigerBeetle diverge.

**Rung 5: let-it-crash, supervision, and the containment guarantee.** When a process hits an error it cannot handle, the idiom is to let it crash: the process dies rather than trying to limp on in a corrupted state. A **supervisor** is another process whose only job is to watch its children and restart them according to a declared policy when they die. The pair (crash plus supervised restart) is a recovery mechanism. Here is the thesis of the entire document: that mechanism is only a *guarantee* because of rung 2. When a process crashes, restarting it to a clean known state is *safe* precisely because state isolation guarantees the crash could not have corrupted anyone else. The crashed process shared no mutable memory with its siblings, so its corruption was confined to its own heap, which is being thrown away in the restart. Without rung 2, "restart the crashed process" would be a hope, not a guarantee, because the crash might have left damage in shared state that the restart does not touch. With rung 2, the blast radius of any fault is exactly one process. This rung uses rung 2 (isolation makes restart safe), rung 4 (the crashed process was the only writer of its state, so there is a clean boundary to restart to), and rung 1 (a crashed or wedged process cannot prevent the supervisor from running).

**The thesis, stated plainly.** Rungs 0, 4, and the *shape* of 5 (the supervision structure) are the parts a library can reproduce, because they are matters of API and program structure. Rung 2 is what upgrades rung 5 from a restart **mechanism** into a restart **guarantee**, and rung 2 lives in the runtime, not the API. A long-running handler being preempted (rung 1) also lives in the runtime. So the properties that make let-it-crash trustworthy are exactly the ones you cannot get by copying the actor interface. That is the whole argument; sections 6 and 7 make it concrete.

## 4. The two isolations

The word "isolation" is overloaded and the overload hides the argument, so split it into two distinct properties.

**State isolation** (rung 2) is a property of *memory*: execution units share no mutable memory. Synonym: shared-nothing.

**Fault containment** is a property of *failure*: a failure in one execution unit cannot damage another. The boundary inside which a fault's effects are confined is the **fault-containment region** (defined canonically in [dependability.md#threats](./dependability.md#threats)). The amount of system one fault can take down is its **blast radius**. The resilience metaphor for a containment boundary is the **bulkhead**, after the watertight compartments that keep a hull breach from sinking a ship.

These are different properties: one is about memory, the other about failures. The central claim that ties them is causal and one-directional. **State isolation mechanically guarantees fault containment.** If two units share no mutable memory, then a failure in one *cannot* have corrupted the other's state, because there was no shared state to corrupt. The memory property forces the failure property. This is why rung 2 is load-bearing for rung 5: it is the only thing that turns "we restarted the crashed process" into "the crash was contained to that process."

The implication runs only one way. State isolation gives you fault containment for free. But you can pursue fault containment by other routes without state isolation (hardware memory protection does it across OS processes; a type system can do it at compile time), and you can have execution units that serialize access to state (rung 4) without isolating that state (rung 2), in which case you do *not* get the containment guarantee. The full treatment of these alternative routes, including the recurrence across the OS, the BEAM, and the type system, lives in [dependability.md#cross-cutting-patterns](./dependability.md#cross-cutting-patterns). Section 8 gives the short version of the historical part.

## 5. Supervisor as control plane

A supervisor is a **control plane**; the workers it manages are the **data plane**. The distinction, defined in full in [dependability.md#cross-cutting-patterns](./dependability.md#cross-cutting-patterns): the control plane *decides what to do* (its work is O(1) in the request, may be branchy, and runs rarely), while the data plane *does it* (O(N) in the request, must stay tight, runs constantly). A supervisor does no application work. It holds a restart policy and a list of children, and it acts only when a child dies. That is a control plane in the precise sense: branchy decision logic that fires on events, not on the hot path.

This split is what keeps recovery logic from contaminating the work. The worker process is pure data plane: it handles requests and knows nothing about restart policy, escalation, or its own supervision. The supervisor is pure control plane: it knows the policy and nothing about the work. Because the worker carries no recovery logic, it is free to follow let-it-crash and simply die on an error; the decision about what to do next lives one level up, in the plane built to make it.

Supervision is **fractal**. A supervisor can supervise other supervisors, which supervise workers, forming a **supervision tree**. The same control-plane/data-plane relationship holds at every level: each supervisor is the control plane for the subtree beneath it, and is itself a child (data plane, from its parent's view) of the supervisor above. A failure that one supervisor cannot resolve by restarting its children escalates: the supervisor itself dies, and its parent treats that as a child failure and applies its own policy. Recovery happens at the lowest level that can contain it, and escalates only as far as it must.

The granularity is the distinguishing feature. The BEAM does all of this **in the runtime**, at process granularity, with restart latencies in the microsecond-to-millisecond range and a blast radius of one process. The same control-plane/data-plane recovery pattern exists at the orchestration layer (Kubernetes restarting a crashed pod), but there the unit is a pod, the latency is seconds to minutes, and the blast radius is a whole pod's worth of work. Same pattern, different granularity, and the granularity is most of what you are buying. Section 8 and [dependability.md#the-mttf-and-mttr-lever](./dependability.md#the-mttf-and-mttr-lever) develop why granularity is the lever.

## 6. Porting the API is not adopting the properties

State the principle directly: **porting the actor API is not the same as adopting the BEAM's properties.** The properties live in the runtime, not the API.

An actor API is a surface: spawn an actor, send it a message, define a handler, declare a supervision strategy. Any language can offer that surface, and many do. But the surface is rungs 0, 4, and the shape of 5. The guarantee that makes the surface trustworthy comes from rungs 1, 2, and 3, which are enforced by the runtime: reduction-counted preemption, per-process private heaps with no expressible cross-heap reference, and copy-on-send. A library bolted onto a runtime that does not enforce those things gives you the same method calls and a different set of guarantees, specifically a weaker set, and the difference is invisible until something crashes.

The test for whether a given property is portable: ask whether it is a fact about the *API* (the shape of what you call) or a fact about the *runtime* (what the machine enforces below the API). Rung 0 is API plus a cheap-spawn implementation, portable. Rung 4 is API structure, portable. The shape of rung 5, the supervision tree, is API structure, portable. Rungs 1, 2, 3 are runtime enforcement, and a library cannot retrofit them onto a runtime built on shared-memory threads. The next section walks the most carefully built actor library on exactly this test.

## 7. Worked example: Akka

Akka is the actor model on the JVM, and it is the right counter-example because it is *good*: it copies OTP's supervision faithfully, it has cheap actors, and its designers understood the BEAM well. Walking Akka rung by rung shows precisely which properties a serious library can carry across and which it structurally cannot, no matter how well built.

| Rung | Property | BEAM | Akka | Why |
| --- | --- | --- | --- | --- |
| 0 | Cheap process | yes | **yes** | Akka actors are cheap objects; millions are feasible. Pure structure, ports cleanly. |
| 1 | Per-unit preemption | yes | **no** | No actor-level preemption. A long message handler starves its dispatcher thread. The OS preempts threads, not actors, and the actor is below the thread, so it is invisible to the OS scheduler. |
| 2 | State isolation | yes | **no** | One shared JVM heap. Isolation between actors is convention, not enforcement: nothing stops you sharing a reference. |
| 3 | Message passing by copy | yes | **no (local)** | Local messages are passed by reference for speed. Copying happens only across the network. So locally there is no copy boundary. |
| 4 | Serialized state access | yes | **yes, conditionally** | An actor processes one message at a time, so its own state is serialized, but the serialization is only as strong as rung 2's discipline (see below). |
| 5 | Let-it-crash + containment | guarantee | **mechanism yes, guarantee no** | Akka has full supervision copied from OTP. But with a shared heap, a crash may already have corrupted shared state, so restart is only as safe as discipline. |

Read the table by the runtime/API split from section 6 and the pattern is exact.

Akka gets every rung that is pure API or program structure. **Rung 0:** cheap actors are an implementation detail of the library, and Akka has them. **Rung 4:** one-message-at-a-time dispatch is a property of how the library pumps the mailbox, and Akka does it, so an actor's own fields are accessed serially as long as nobody else touches them.

Akka structurally cannot get the rungs that live in the runtime. **Rung 1:** preemption granularity is set by the JVM and the OS, both of which schedule threads, not actors. An actor is a unit *below* the thread, invisible to the preempting scheduler, so a handler that runs long simply occupies its dispatcher thread until it returns; there is no reduction counter to cut it off. **Rung 2:** the JVM has one shared heap, and Java/Scala references can point anywhere in it. Keeping actors isolated is a coding convention ("don't share mutable references in messages"), and conventions can be violated, including by accident. **Rung 3:** for local sends, Akka passes the message by reference to avoid copy cost, which means a mutable object handed to another actor is now reachable from two actors at once.

The two conditional rungs are where the dependency on the missing rungs shows. **Rung 4 is conditional on rung 2.** An actor serializes access to its own state, but if you leak a mutable reference into a message (rung 3 makes this easy, rung 2 does not stop you), two actors now hold the same object and the serialization evaporates: both can mutate it concurrently, each thinking it has exclusive access. The serialization is real only to the extent the isolation discipline holds. **Rung 5 is mechanism-yes, guarantee-no.** Akka's supervision is a faithful copy of OTP: supervisors, strategies, escalation, the whole tree. The restart *mechanism* is all there. But the *guarantee* is not, because the guarantee was never in the supervision code. It was in rung 2. With a shared heap, a crashing actor may already have corrupted state that another actor can see, and restarting the crashed actor to a clean state does nothing about that damage. So the restart is exactly as safe as the isolation discipline, which is to say: safe by convention, not by construction.

The pattern, stated once: **Akka gets the rungs that are pure API or structure (0, 4, the shape of 5) and structurally cannot get the rungs that live in the runtime (1, 2, 3, and therefore the guarantee in 5).** This is not a knock on Akka's engineering. It is the demonstration that the BEAM's payoff cannot be delivered by a library on a shared-memory runtime, because the payoff *is* the runtime enforcement. Port the API and you get the mechanism. The guarantee stays behind.

## 8. Historical lineage

The BEAM did not invent this idea. The operating system discovered it first, and the recurrence is worth seeing because it shows the property is fundamental rather than an Erlang quirk. The full treatment is in [dependability.md#cross-cutting-patterns](./dependability.md#cross-cutting-patterns); here is the short version.

A 1950s machine ran one program at a time and needed no isolation: with a single job, there was nothing to contain it from. Then came the resident **monitor**, a small supervisory program that stayed in memory and loaded user jobs one after another, the ancestor of the OS kernel. The monitor created three new failure modes, because now a user job shared a machine with code that had to survive it, and each failure mode forced a hardware mechanism that is one of our rungs:

- A job could scribble over the monitor's memory. The fix was **memory protection**: base/limit registers, then the MMU and per-process address spaces, which make one job's writes physically unable to reach another's memory. That is hardware-enforced **state isolation**, rung 2, with the address space playing the role of the private heap.
- A job could loop forever and never return control. The fix was the **timer interrupt**: hardware forcibly returns control to the monitor on a fixed schedule. That is hardware-enforced **preemption**, rung 1, with the timer interrupt playing the role of reduction counting.
- A job could issue raw I/O and corrupt devices. The fix was **dual-mode operation** (user mode versus supervisor mode), restricting privileged operations to the monitor.

So the mapping is exact: the kernel **is** a supervisor (a control plane managing data-plane jobs), the timer interrupt **is** reduction counting (forced preemption), and the address space **is** the private heap (enforced state isolation). The BEAM's novelty is not the idea. It is the **granularity** and **cost**. The OS enforces containment at the address space, which costs kilobytes to megabytes and a kernel-mediated context switch, so you get a handful of them per machine. The BEAM moves the same containment property to a unit costing hundreds of bytes and microseconds, cheap enough to be the *default* unit of program structure: one process per request, per connection. And it changes the enforcement layer from hardware (the MMU refusing an out-of-bounds write) to the language runtime (there is no expressible cross-process shared mutable reference to begin with). Same property, two orders of magnitude finer and a layer up the stack. See [dependability.md#enforcement-layers](./dependability.md#enforcement-layers) for the enforcement-layer map this points at.

## 9. What's contested

The argument above is not unopposed, and the strongest objections are worth stating in their own terms.

**Structured concurrency and effect-system supervisors.** Libraries like Cats Effect (Scala) and the structured-concurrency facilities in newer languages provide supervised, cancelable fibers with strong composition guarantees: a parent scope cannot complete until its children do, cancellation propagates cleanly, and resource cleanup is guaranteed. The objection is that these deliver much of what supervision delivers, with stronger compositional properties than OTP's, on runtimes that are not the BEAM. The response from the BEAM side is that these systems still run on a shared heap, so they inherit Akka's rung-2 gap: their supervision is excellent at *control-flow* recovery (cancel a subtree, clean up resources, restart a computation) but does not provide the *memory* containment guarantee, because a fiber can still corrupt shared mutable state before it fails. They are answering a real and partly different question (compositional cancellation and resource safety), and they answer it well; they are not answering the containment question.

**Valim's guarantee-not-capability point.** José Valim (creator of Elixir) frames the distinction as capability versus guarantee, which is the same split this document draws between mechanism and guarantee. Many runtimes have the *capability* to do supervised restart. The BEAM's claim is to a *guarantee*: that restart is always safe because isolation is always enforced. The contested question is how much that guarantee is worth in practice versus a capability plus discipline, and reasonable engineers disagree. On systems where the isolation discipline is well maintained and tooling catches violations, the practical gap may be small. The BEAM position is that "always enforced, cannot be forgotten" is categorically different from "enforced when we remember," especially under the conditions (3am, an unfamiliar code path, a junior change) where discipline fails and you most need the guarantee.

**The granularity and latency rebuttal.** A counter to "but Kubernetes also does supervision" is that the BEAM and the orchestrator are not substitutes, because their granularity and latency differ by orders of magnitude. The BEAM contains and recovers a single process in microseconds inside one VM; the orchestrator contains and recovers a whole pod in seconds-to-minutes across machines. They compose (a BEAM node sits inside a pod) rather than compete, and arguing that one obviates the other mistakes a coarse outer bulkhead for a fine inner one. This is less a contested point than a clarification, but it recurs often enough to state.

## 10. Where the BEAM is weak

The containment story is strong, and it is bought with costs that are worth naming, especially against a culture like TigerStyle (the TigerBeetle engineering discipline, treated in [dependability.md#the-mttf-and-mttr-lever](./dependability.md#the-mttf-and-mttr-lever)) that prizes bounded, static, predictable resource use. On several of TigerStyle's axes the BEAM is the opposite, by design.

**Unbounded mailboxes.** A process's mailbox grows without a built-in limit. If a process receives faster than it handles, the mailbox grows until the VM runs out of memory, and because state isolation means the messages are copies sitting in that process's heap, the growth is real memory. This is the BEAM's most cited failure mode: a slow consumer behind a fast producer is an unbounded queue, and the runtime will not stop it for you. Compare TigerStyle, where every queue is statically bounded and overflow is a designed-for condition, not a memory leak.

**Manual backpressure.** Because mailboxes are unbounded, **backpressure** (the mechanism by which a slow consumer tells a fast producer to slow down) is not automatic. You build it yourself: explicit acknowledgements, bounded work pools, libraries like GenStage that add demand-driven flow control on top of the raw primitives. The runtime gives you the isolation but not the flow control, so the discipline the BEAM removes at rung 2 (you cannot forget to isolate) it reintroduces here (you can absolutely forget to bound).

**Dynamic allocation and recursion.** Rung 3's copy-on-send means messages allocate, per-process heaps grow and are garbage-collected, and idiomatic Erlang leans on recursion and short-lived allocation rather than fixed buffers. This is the direct violation of TigerStyle's static-allocation rule (allocate everything at startup, never in steady state). The BEAM's bet is the opposite bet: dynamic allocation plus cheap per-process GC, accepting GC and allocation cost to buy the isolation and the programming model. Both bets are coherent; they optimize for different things ([dependability.md#the-mttf-and-mttr-lever](./dependability.md#the-mttf-and-mttr-lever) frames them as fault tolerance versus fault prevention, two cultures with the same priority order).

The honest summary: the BEAM optimizes for low MTTR (recover in microseconds, contain to one process) and accepts a runtime full of dynamic, unbounded, hard-to-statically-bound behavior to get there. A prevention-first culture optimizes for high MTTF (never break in the first place) and would not accept an unbounded queue anywhere. They are not competing for the same prize, and the BEAM's weaknesses are the visible price of the trade it chose.
